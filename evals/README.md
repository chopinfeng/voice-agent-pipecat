# 端到端评测

用 pipecat 自带的 `pipecat eval`。场景是 YAML，跑起来会真的合成用户语音喂给 bot、
听它实际念出来的音频、再交给 judge 模型按自然语言判据打分。

```bash
evals/run.sh                      # 全部六条
evals/run.sh interrupt_storm      # 只跑一条
```

## 六条场景，每条对应一个真实故障

| 场景 | 当初怎么坏的 |
|---|---|
| `interrupt_storm` | 打断时助手说了一半的回复被整个丢掉，上下文里连着几条用户发言没有助手消息，模型不记得说过什么，连着四轮复读 |
| `search_interrupted` | 联网查询期间不出声，用户等两秒就重问，重问即打断，打断取消了「结果回来后念出来」那轮——七次查询四次结果没念出来 |
| `task_visible` | 联网查询不登记进任务表，问「有什么在跑」答「没有」，而当时搜索正在飞 |
| `compute_dispatch` | 让它算斐波那契数，答「没有这个能力」——其实沙箱放行 python3，卡点是提示把 agent 框死在「回答代码项目的问题」上 |
| `no_fabrication` | 问不存在的东西时编一个像样的答案，答过「支持 PostgreSQL、Redis」 |
| `bystander` | 内部标记（`[skip]`、`[主用户]`）被当成内容念给用户听，发生过三次 |

新增场景时**必须在文件头写清楚它对应哪个故障**。写不出来说明这条没有来由，
半年后没人敢删也不敢改。

## 三个容易踩的点

**打断要用 `send_after`，不能写死秒数。**真实语音链路有七八秒往返（按真实节奏喂音频、
VAD 判定、听写、LLM），照绝对秒数排的话，「第 4 秒插话」会落在第一句还没被听写出来
之前——那不是打断，是自言自语，测的东西跟想测的完全无关。用
`send_after: {event: llm_started, delay_ms: 1500}`，锚在真实事件上，换了更快或更慢的
模型也不用重排时间表。

**判据写成自然语言，别写关键词。**judge 看的是意思。关键词匹配在这个项目里翻车过
三次：中文数字（「五百七十三万」对不上 `5736396`）、否认的同义说法（只认「没有」，
把「没连数据库」判成错）、以及「八月十五号是周六」因为含「五」被判成对。

**跑之前机器要干净。**`run.sh` 会查残留的 `voice_bot` 进程和机器负载，不干净就拒跑。
这两样能把本地听写从 0.7 秒拖到 62 秒，延迟判据全部失真——那种数据比没有更糟，
因为它看起来像真的。

## judge 为什么指到 DeepSeek

官方默认用本机 ollama（没装），OpenAI 直连在当前网络下是 403。`run.sh` 靠
`OPENAI_API_KEY` / `OPENAI_BASE_URL` 把 `openai` 服务指到 DeepSeek 官方——快、有额度，
也符合「只用国产开源模型」。

## 用户语音为什么用 Kokoro

官方 harness 只支持 kokoro 和 cartesia 合成用户语音。Kokoro 本地跑、不要 key、
中文音色是 `zf_xiaoxiao`。**音色必须跟语言配套**——`af_heart` 是美音，`language: zh`
也念不出中文。

（顺带一提：Kokoro 之前作为 bot 的 TTS 试过，因为首帧慢一个数量级被否掉了。
但在评测里它只用来合成用户台词，不在延迟关键路径上，慢一点无所谓。）

## `attic/` 里那套不要用

迁过来之前我自己写了一套（六百行），后来发现 `pipecat.evals` 早就有这一切且更强。
`attic/README.md` 记着那四个自制缺陷。留着只为记录教训。
